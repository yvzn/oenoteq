# 01: Resetting Garde to empty doesn't update the view after saving

**Status:** ready-for-agent
**Category:** bug

## Agent Brief

**Category:** bug
**Summary:** After editing a Wine and saving, the detail/list view can show the pre-edit Garde values (most visible when clearing both bounds), because a stale server read overwrites the local copy before the queued update has synced.

**Current behavior:**
Saving a Wine edit writes the new values to the local store, then queues a PUT in the outbox and fires a background push. The push replays other entity outboxes first, so the PUT lands after the user has already navigated to the detail view. The detail load, while online, immediately re-reads the Wine from the server and writes that response into the local store — the server hasn't received the PUT yet, so the old `garde_debut` / `garde_fin` come back and overwrite the user's edit. The view then shows the old range. Nothing refreshes once the PUT lands.

Verified with a scratch test: after `update()` with `garde_debut: null, garde_fin: null`, the local store holds nulls; a following `load()` with the server still returning the old wine yields `2020 / 2028` in both the view state and the local store. The same race affects any edited field, not only clearing Garde; clearing is just where it was noticed.

**Desired behavior:**
A saved edit is never visually reverted by a read of server state that predates it. While a Wine still has a pending outbox update (or create), the local copy is authoritative for display; server reads must not overwrite it. Once the update has synced, the next read converges on server state.

**Key interfaces:**
- The Wine detail load path (`useWines.load` / `pullWine`): must not overwrite a Wine that has a pending outbox item
- The bulk replication (`pullWines`): same guard, it currently replaces local Wines wholesale
- The "not yet synced" badge logic already knows how to detect pending items per Wine — reuse that notion rather than inventing a second

**Acceptance criteria:**
- [x] Test: edit a Wine clearing both Garde bounds, then load detail with the server still returning the old values → view and local store keep `null` / `null`
- [x] Same test for changing Garde to different non-empty values
- [x] After the outbox update syncs, a subsequent load reflects the server's (now matching) values
- [ ] List view after save also reflects the edit (cellar list, online, with the PUT not yet landed)
- [x] Wines with no pending items are still refreshed from the server as before

**Out of scope:**
- Redesigning the outbox flush order
- Quantity handling (already delta-based, ADR 0006)
- The Garde end auto-fill on blur of Garde start (separate behavior, unchanged)

Implemented in `93c3587`. `pullWine` and `pullWines` (`web/src/sync/wineSync.ts`) now skip a Wine that still has a queued outbox item, reusing `isQueued`. Tests in `wineSync.test.ts`.

**Not done:** list-view criterion. `CellarListView` reads `/search` directly via `useSearch`, not the local store, so the list can still show old values until the PUT lands. **Known narrow gaps:** a PUT syncing between the GET response and the `isQueued` check can still let a stale response overwrite the store; a queued Wine with no local copy falls through to the server write.
